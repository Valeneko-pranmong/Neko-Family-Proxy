## 3. Candidate payload layout expected by the installer builder

`--candidate-dir` is the **stage root**; the script reads `<root>\payload\...` and writes

```text

    NekoLauncher.exe            # must equal --launcher-sha256
    NekoUpdater.exe             # must equal --updater-sha256

```

## 4. Envelope (release-v2) — the two traps

**Trap 1: use the right signer.** `scripts/sign_software_release.py` cannot sign a
release-v2 payload: it parses through the legacy `parse_release_set`, which accepts only
`schema_version 1` and `channel = "beta"`. Use:

```powershell
& $B scripts\build_software_release_v2.py `
  --input  "$W\release-payload.json" `
  --launcher-artifact "$W\r-dist\NekoLauncher.exe" `
  --updater-artifact  "$W\r-dist\NekoUpdater.exe" `
  --core-artifact     "$W\NekoProxyCore.zip" `
  --private-key-file  "<custody path>\neko-update-prod-3.pem" `
  --key-id            neko-update-prod-3 `
  --public-key-file   "<32-byte raw public key file>" `
  --output            "$W\release-v2.json"
```

* `--output` must be named `release-v2.json` and the artifact names must be exactly
  `NekoLauncher.exe`, `NekoUpdater.exe`, `NekoProxyCore.zip`,
  `NekoFamilyProxy-Installer.exe` (`EXPECTED_ASSETS` is enforced).
* `--public-key-file` must be either raw 32 bytes or a PEM — a `.pub.hex` text file with a
  trailing newline fails with `PUBLIC_KEY_INVALID`.
* The builder canonicalizes, signs, **verifies its own signature**, and refuses to write if
  an artifact changed mid-build (`ARTIFACT_CHANGED_DURING_BUILD`).
* Release keys are guarded by a custody reference in some tools: `NEKO_RELEASE_KEY_REF`
  (see `sign_software_release.production_key_reference`) lets you point at an existing
  custody file instead of copying a private key to a new location. Prefer that.

**Trap 2: framing.** The envelope must be exactly canonical JSON. Revisions 1–6 carried a
1,641-byte file with a trailing newline (`0a5f3fb3…`) that every older gate stripped before
comparing, so it was baked into the installer unnoticed; clients download the bytes as-is
and reject it, so it could never be published. `build_beta_installer.py` now requires
`canonical_json_dumps(doc) == raw bytes`. Revision 8's canonical envelope is 1,640 bytes
ending `}`.

**Sequence allocation is not yours to invent.** `scripts/release_controller.py` reads
`<repo>\authority\production_sequence_ledger.jsonl` and fails closed when no explicit ledger
allocation is supplied. That ledger is on the custody host. On this host the revision 8
envelope was signed directly with `build_software_release_v2.py` (sequence 24) and **no
ledger record was written** — reconcile 24 (and every later sequence) on PC ADV before
publication.

## 5. Installer build

```powershell
& $B installer\scripts\build_beta_installer.py `
  --candidate-dir     "$W\stage" `
  --launcher-sha256   <launcher hash> `
  --updater-sha256    <updater hash> `
  --core-authority    b7d9708bc2c9a97255a9ea2f8307ef66e2d81bf8 `
  --release-version   5.2.2 `
  --baseline-envelope "$W\stage\payload\baseline\release-v2.json" `
  --trust-profile     "$W\stage\payload\trust\update-profile-v1.json"
```

Eleven gates run before ISCC and all must print `PASS`: launcher hash, updater hash +
self-check, Core manifest (1,023 files, no extras), trust profile, baseline envelope,
v2ray pin, .NET pin, secret hygiene, installer source + driver-script pin, driver pins,
then `BUILD=PASS`. Output: `<stage>\out\NekoFamilyProxy-Installer.exe` +
`build-record.json`.

The installer fails closed if the envelope's `launcher.installed_identity_sha256` does not
equal the staged `NekoLauncher.exe` — so **any** binary change forces a new envelope and a
new sequence. That is why a rebuild cannot reuse `preview-0023`.

## 7. Known constraints handed over with this line

1. **Authenticode is still not applied.** This host has no `signtool` / Windows SDK and no
   code-signing certificate (`CN=localhost` and `CN=SteelSeries A/S` only). Signing needs
   the operator certificate the owner has not procured. Never describe these artifacts as
   signed.
2. **`preview-0024` / sequence 24 is not in the ledger** (see section 4). Reconcile before
   publish, tag or deploy.
3. **Version 5.2.2a is preview-classified**: preview-only guards recognise `5.2.2a`/`5.2.2a0`.
   A `5.2.2` stable release needs the stable profile `trust/update-profile-v1.json`
   (channel `stable`, authorizes `neko-update-prod-3` — verified present) and a stable
   release id/sequence.
4. **`minimum_supported_sequence` is set to its own sequence** in every 5.2.x preview, which
   makes each revision a forward-only step; an installed older preview cannot adopt an
   envelope with a higher minimum. Decide the value consciously for 5.2.2.
5. **Launcher login flow requires the staging identity origin** pinned into the frozen
   build (`RELEASE_IDENTITY_BASE_URL`, see commit `a044974`); the frozen configuration
   rejects `NEKO_PROXY_API_URL` overrides. Confirm the intended origin before a stable build.
6. Interactive Discord login and Settings behaviour on revision 8 have unit coverage and
   `--tk-self-test`, but **no live sign-in evidence** yet.
7. Repository-level tests: `76 passed`, plus one environment-dependent E2E test
   (`tests/test_e2e_release_pipeline.py::test_release_controller_e2e`) that requires the
   historical `E:\Github\artifacts` path. It fails on hosts without that path; treat it as
   an environment gap, not a code defect.
8. Three obsolete local branches on this host (`docs/p0-launcher-contract`,
   `feat/proxy-api-launcher-slice-1`, `feat/proxy-api-launcher-slice-2`) are ancestors whose
