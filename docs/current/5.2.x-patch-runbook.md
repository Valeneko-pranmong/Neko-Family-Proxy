## 1. ข้อห้าม / invariant ที่ห้ามฝ่าฝืน

1. **Updater bytes ถูก pin ที่ `b0b991f5…`** ตลอด line 5.2.x
   - ห้าม rebuild/เปลี่ยน `NekoUpdater.exe` โดยไม่มีแผน migration
   - manifest ของรุ่นถัดไปต้องระบุ hash นี้; installer ต้อง stage ไฟล์เดียวกัน
   - version label ใน manifest = tag ได้ (publisher บังคับ) แต่ **ไบต์ต้องเป็น b0b991f5…**
2. **Pipeline ไม่เคย stage/แทนที่ updater** (`software_update_stage.py`) — feed เปลี่ยน updater ให้ client เองไม่ได้
3. **Feed หนึ่งตัวรับ updater hash ได้ค่าเดียว** — เครื่องที่ยังใช้ `35f4532c…` (5.2.2 และ 5.2.3 ชุดแรก) และเครื่องที่ใช้ `b0b991f5…` (5.2.3 re-release) อยู่ feed เดียวกันไม่ได้
4. **Core ถูก freeze 5.2.0** (`c262432c…`) — ห้าม rebuild Core หรือเปลี่ยน manifest schema โดยไม่แก้ verifier และวางแผน migration
5. **Sequence ต้องเดินหน้าเท่านั้น** — ห้าม reuse sequence ที่เครื่องใดอาจบันทึกเป็น failed (seq 27 ถูกใช้โดย 5.2.3 ชุดแรก; seq 28 ถูกใช้โดย re-release)
6. **`releases/latest` คือช่อง discovery ของ stable** — release ที่เป็น manual ต้อง publish แบบ non-latest
7. **Installer ไม่รองรับติดตั้งทับคนละเวอร์ชัน** — migration คือถอน → ติดตั้งใหม่ (credential ต้อง login ใหม่; วัน/สิทธิ์อยู่ฝั่ง server)

## 4. Diagnostic codes ที่เจอบ่อย

| Code | ความหมาย | ทางแก้ |
|---|---|---|
| `UPDATER_SIZE_MISMATCH` / `UPDATER_INCOMPATIBLE` | installed updater ≠ manifest | ตรวจ population; ต้อง manual install หรือ bridge; ห้ามฝืน feed |
| `CORE_INVENTORY_INVALID` | Core manifest schema ไม่ตรงกับ verifier | ตรวจว่า verifier รองรับ legacy schema; อย่า publish |
| `SAME_SEQUENCE_IDENTITY_CONFLICT` | ใช้ sequence ซ้ำกับ payload คนละตัว | bump sequence |
| `DOWNGRADE_REJECTED` | feed seq < highwater (เช่น เครื่องเคยพังที่ 27 แต่ latest 26) | คาดได้; login ยังได้ถ้าไม่มี pending; รุ่นถัดไปใช้ seq สูงกว่า |
| `REINSTALL_REQUIRED` | updater mismatch/รุ่น major ใหม่ | ติดตั้ง installer ใหม่ |
| login ถูกบล็อก + pending | pending ค้างจาก apply ล้มเหลว | relaunch หลัง failed จะข้าม pending; ถ้าจำเป็นให้ย้าย/ลบ `update-pending` |
| latest เปลี่ยนเอง | `gh release edit` | PATCH `make_latest=false` และ force v5.2.2 latest |

## 5. ถ้าจำเป็นต้องแก้ updater จริง ๆ

การเปลี่ยน updater hash จะทำให้ **ทุกเครื่องที่ติดตั้งอยู่** resolve ไม่ผ่าน (feed ระบุ hash ใหม่ แต่เครื่องมี hash เก่า) และ pipeline ไม่สามารถส่ง updater ใหม่ให้ได้

ทางเลือก:
- **A. หลีกเลี่ยง:** แก้เฉพาะ launcher/core ที่ไม่กระทบ updater
- **B. Migration line ใหม่:** ต้องมี installer/bridge ที่ผู้ใช้รันเองหนึ่งครั้ง แล้วค่อยออก feed ที่ระบุ updater ใหม่ — วางแผนช่วงเปลี่ยนผ่านและอย่าให้ feed stable ไปบล็อกคนที่ยังไม่ย้าย
- **C. Self-replace ในอนาคต:** ต้องออกแบบและทดสอบแยก (ยังไม่มีใน 5.2.x)
