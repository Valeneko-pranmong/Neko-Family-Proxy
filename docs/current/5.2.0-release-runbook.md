# Neko Family Proxy 5.2.0 Release Runbook

**Status:** BLOCKED — preparation only; not executable
**Release line:** `v5.2.0`
**Channel:** preview/manual
**Upgrade policy:** clean uninstall-first
**Source branch:** `feat/proxy-api-launcher-clean-v2`
**Source commit at preparation:** `2179406` plus the release-preparation commit

This runbook is the release path for the unified Proxy API line. It must not
be used to publish, tag, push, or deploy. Every gate must pass and the owner
must approve the release configuration, signing material, and artifact
destination before any publication step.

- [ ] 01c identity staging E2E passed and the new token endpoint is deployed.
- [ ] 02d Proxy API slice 2B is deployed to staging.
- [ ] 03c live E2E passed: Discord login, `/v1/me`, claim, heartbeat,
      launch permit + Runtime Config v1, Core start, release on exit.
- [ ] Negative E2E cases passed: suspended/banned, missing app access, expired
      license, second-installation conflict, ambiguous refresh, wrong
      audience/scope.
- [ ] Owner approved the HTTPS `NEKO_PROXY_API_URL` origin for the 5.2.0 build.
- [ ] Owner approved the release payload, Core authority, trust profile, signing
      material, and artifact destination.
- [ ] Installer payload and prerequisites are staged outside the repository.
- [ ] A clean Windows VM and a 5.1.6 installation are available for the matrix.

Do not proceed if any item is open.

## 3. Release configuration

- Channel: preview. Use `trust/update-profile-preview-v1.json`. 5.2.x must not
  be promoted to stable while 5.1.6 is the fallback.
- `NEKO_PROXY_API_URL`: only the owner-approved HTTPS origin. It must have no
  path, query, fragment, credentials, or trailing path. It must be mutually
  exclusive with `NEKO_AUTH_BRIDGE_URL`.
- No `NEKO_AUTH_BRIDGE_URL`, Supabase URL, publishable key, session, cookie, or
  direct proxy database access in the 5.2.0 runtime path.
- No admin service token, service-role key, signing private key, or other
  secret in the Launcher, installer, logs, or build artifacts.
- The current frozen-build guard rejects `NEKO_PROXY_API_URL` and requires the
  legacy bridge. A release build therefore cannot be produced until the owner
  approves the release configuration and the guard change is implemented and
  tested. Do not bypass the guard manually.
- The preview trust profile and the baseline envelope must verify before the
  installer build. The baseline envelope is not present in the repository and
  must be produced through the approved release-signing process.

## 4. Build the Launcher, Updater, and installer

1. Build `NekoLauncher.exe` and `NekoUpdater.exe` from the frozen source with
   the approved release configuration. Verify the Launcher starts only with
   the approved Proxy API configuration and does not load the Supabase gateway
   in proxy mode.
2. Stage the approved payload outside the repository:

   ```text
   <stage>\payload\NekoLauncher.exe
   <stage>\payload\NekoUpdater.exe
   <stage>\payload\CoreBundle\   (complete bundle with core-manifest.json)
   <stage>\payload\Prereqs\windowsdesktop-runtime-6.0.36-win-x64.exe
   ```

3. Build the installer with the approved authorities:

   ```text
   python installer\scripts\build_beta_installer.py ^
     --candidate-dir <stage> ^
     --launcher-sha256 <approved-launcher-sha256> ^
     --updater-sha256 <approved-updater-sha256> ^
     --core-authority <approved-core-commit> ^
     --release-version 5.2.0 ^
     --baseline-envelope <approved-release-v2.json> ^
     --trust-profile trust\update-profile-preview-v1.json
   ```

4. Preserve the fail-closed gates: running-process check, uninstall
   `DisplayVersion` check, exact `MyAppVersion` guard, launcher/updater hashes,
   Core manifest and per-file hashes, `v2ray-sn.exe` pin, .NET bootstrapper
   pin, secret hygiene, helper scripts, and driver pins.
5. Record the installer size, SHA-256, build record, source commit, dependency
   lock hash, Core manifest hash, payload hash, trust profile hash, and
   baseline envelope hash.

## 5. Install and rollback matrix

Run every case on a clean Windows VM:

1. Clean install on a machine with no Neko Family installation.
2. 5.1.6 installed -> uninstall 5.1.6 -> install 5.2.0 -> launch -> Discord
   login -> Core start/exit.
3. Uninstall 5.2.0 and reinstall; confirm start-from-clean behavior and that
   the shared netfilter2 driver remains.
4. Rollback: uninstall 5.2.0 -> install the frozen 5.1.6 installer -> legacy
   login -> Core start/exit.
5. Negative installer cases: Launcher/Core/Updater running, unknown installed
   version, different installed version, missing Core manifest, hash mismatch,
   missing .NET runtime, and driver failure.

The clean uninstall-first policy means local state, preferences, trust,
baseline, and logs are not preserved across the line change. Document the
result for each case; do not claim an in-place upgrade.

## 6. Staging E2E

Use a real staging identity and a linked proxy account with an active license:

1. Discord login through the Launcher.
2. `/v1/me` returns the active account and license.
3. Claim returns `session_id`, heartbeat interval, and license validity.
4. Heartbeat succeeds at the server-provided interval.
5. `/v1/launch-permit` returns a permit and Runtime Config v1.
6. Core starts with the permit and the proxy connects.
7. Release on exit succeeds.

Negative cases:

- suspended/banned account -> no token or no launch;
- missing app role -> authorize denied;
- expired or inactive license -> claim/permit denied;
- second installation claim -> latest-claim-wins and displaced session gets
  `session_conflict`;
- ambiguous refresh -> token cleared and interactive login required;
- wrong audience/scope -> 401/403.

Verify no Supabase URL/key/session, no bridge call, and no proxy database
access in the new-line process, logs, and network traffic. Record redacted
status codes, request/correlation IDs, deployment IDs, permit verification
result, and Core start/exit evidence. Never record tokens, permits, runtime
credentials, or keys.
