## 1. Support diagnostics

- The support log schema is now version 2 and always records machine/runtime
  context: local and UTC timestamps, timezone, OS version/build, architecture,
  CPU count, locale, launcher executable path, log directory, install root, free
  disk space, and Core hashes/path.
- Structured events are written under `AUTH`, `APP`, `GAME`, `TELEMETRY`,
  `UPDATE`, and `CORE` categories. Auth events include the browser flow phases,
  token exchange, manual-login timing, session restore timing, and
  `DASHBOARD_READY` for the end-to-end manual-login duration.
- Restore diagnostics distinguish `RESTORE_SUCCEEDED`, `RESTORE_SKIPPED`, and
  `RESTORE_FAILED` without recording credentials. API failures record only
  allow-listed metadata such as error type, safe error code, HTTP status,
  request ID, retryable flag, and WinError.
- Background exception traces, proxy/game/telemetry/update lifecycle changes,
  Settings routes, update checks, and the shutdown summary are recorded.
- Sanitization continues to redact PEM private keys, JWTs, Bearer values, and
  sensitive key-value fields such as tokens, passwords, secrets, credentials,
  recovery codes, PKCE challenges, and API keys. Auth emitters do not include
  OAuth codes, PKCE verifiers, e-mail addresses, or user/session IDs in support
  events.

The purpose is to let users send one local support log for precise diagnosis
without exposing secrets. The log location is shown in the application; no
automatic upload was added.

## 2. Login and Settings presentation

- The pre-refactor 5.2.1 login design is retained: the status row stays pinned
  at the top, the remaining content is vertically centered, and the pending
  login panel floats over reserved space so the login controls do not move.
- The Settings window disables CustomTkinter's Windows titlebar withdraw/re-map
  and reveals the first fully rendered transparent frame in one paint. Thai
  labels no longer appear progressively.
- The existing login copy and bundled Discord icon from 5.2.1 are unchanged.

## 3. Startup auto-login

Automatic session restore itself is unchanged: it uses the saved refresh token,
checks the account, claims a session, and opens the dashboard without asking
the user to sign in again. The presentation around it changed:

- Session restore now starts before the main widgets are built, overlapping the
  network round-trip with UI construction.
- The startup splash stays visible until restore resolves instead of closing
  when the update check finishes. This removes the 2–4 second login-screen
  flash that made users think their session had been lost.
- While waiting, the splash shows `กำลังตรวจสอบการเข้าสู่ระบบ...`.
- A normal close is deferred by one event-loop tick so the authenticated state
  can switch the view to the dashboard before the window becomes visible.
- A force-close cap of 10 seconds prevents an indefinitely stuck splash if the
  restore request never resolves.
- New support events `STARTUP_SPLASH_HELD`, `STARTUP_SPLASH_EXTENDED`, and
  `STARTUP_SPLASH_CLOSED` record whether the splash waited and how long startup
  took. `RESTORE_RESULT` now also includes `startup_elapsed_ms`.
