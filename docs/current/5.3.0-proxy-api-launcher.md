# 5.3.0 Proxy API Launcher — New-Line Direction

**Status:** P1 slices 1–2 implemented in source; source/dev only; not release-ready
**Date:** 2026-10-25
**Repository:** `D:\Neko-Family-Proxy` (Windows Launcher)
**Scope:** new `5.3.0` Launcher line only
**Frozen line:** `5.1.6` remains unchanged

## 1. Decision

The new Launcher line uses:

1. **Neko-NETWORK-ID only** for authentication: Discord browser login, PKCE,
   identity access token, and rotating refresh token.
2. **Neko Proxy API only** for proxy-domain data: account status, license,
   sessions, permits, runtime configuration, coupons, metrics, and audit.
3. **No Supabase key, session, cookie, PostgREST, or RPC access** in the new
   line.
4. **No `launcher_bridge`, no bridge session minting, no synthetic Supabase
   Auth user, and no `launcher_v2.web_sessions` allowlist** in the new line.
5. **No Core contract change.** `NekoProxyCore` keeps its existing permit and
   Runtime Config v1 wire contract.

The target flow is:

```text
Discord browser
   -> Neko-NETWORK-ID /launcher/authorize + /api/launcher/token
   -> Launcher (access token in memory, refresh token in Windows Credential Manager)
   -> Neko Proxy API /v1/me, /v1/session/*, /v1/launch-permit, /v1/coupons/*
   -> NekoProxyCore (fresh permit + Runtime Config v1 over the existing pipe)
```

`launcher_bridge` and the proxy database are not in this path.

## 2. What supersedes the 2026-10-25 bridge plan

The bridge/session-minting portions of
`docs/superpowers/plans/2026-10-25-web-auth-separation-and-5-3-0-cutover.md`
and the bridge implementation notes in `docs/current/web-auth-launcher.md` are
superseded for the new line:

- The new line does not exchange an identity token through `launcher_bridge`.
- The new line does not mint a Supabase session.
- The new line does not create or consume a `launcher_v2.web_sessions` row.
- The new line does not read `launcher_v2.identity_links` or
  `launcher_v2` tables in the Launcher process.
- Neko Proxy API owns the identity-to-proxy-account mapping and session state.

The bridge and `launcher_v2` artifacts remain in this repository only as
legacy/5.1.6 and historical material. No deletion, migration, or production
change is authorized by this document.

## 3. P1 slices 1–2 — implemented scope

Slices 1–2 are deliberately source/dev only. They prove the new authentication
boundary and the full launch path through Neko Proxy API without Supabase or
the bridge. They are an explicitly authorized exception while the broader P0
contract decisions remain open; they are not release-capable and do not close
the P0 register.

Implemented:

- `NEKO_PROXY_API_URL` source-only feature flag (disabled by default).
- Identity-only PKCE exchange through
  `WebAuthClient.authenticate_identity()`; the legacy bridge exchange in
  `WebAuthClient.authenticate()` is untouched.
- `ProxyApiGateway` with bounded HTTPS transport:
  - `GET /v1/me`
  - identity refresh-token exchange at `/api/launcher/token`
  - `POST /v1/session/claim`
  - `POST /v1/session/heartbeat`
  - `POST /v1/session/release`
  - `POST /v1/launch-permit`
- `ProxyApiAuthGateway`:
  - stores only the rotating refresh token in Windows Credential Manager;
  - keeps the access token in memory;
  - calls `GET /v1/me` immediately after a successful web login;
  - refreshes once on `401 invalid_token` / `401 token_expired`;
  - fails closed and clears the refresh token on any failed refresh;
  - maps every shared error code to a Thai user message.
- `ProxyApiEntitlementGateway`:
  - claims with `installation_key_hash`, `display_name`, and
    `Idempotency-Key`;
  - preserves latest-claim-wins and maps `409 session_conflict` to the
    displaced-session behavior;
  - heartbeats with the server-provided interval (10–60 s, stale after 90 s)
    and releases on sign-out/exit;
  - maps account/license/session denial reasons without proxy DB reads.
- `ProxyApiPermitGateway`:
  - calls `POST /v1/launch-permit` with the claimed `session_id`, fresh Core
    challenge, correlation ID, and `Idempotency-Key`;
  - preserves the opaque permit and maps the snake_case API response into the
    frozen Core Runtime Config v1 shape without translation or repair;
  - fails closed on an invalid permit/runtime-config response.
- Proxy mode now composes the real `AuthorizedCoreOrchestrator` and named-pipe
  path; Core process and permit verification behavior are unchanged.
- `LauncherService` claims after login/restore, releases on sign-out/exit, and
  takes the heartbeat interval from the entitlement gateway.
- `app_factory` lazy-imports `SupabaseGateway` only inside the legacy branch;
  proxy mode neither imports nor constructs it.
- The legacy bridge/5.1.6 path remains intact and is selected when
  `NEKO_PROXY_API_URL` is absent.

Not implemented in slices 1–2:

- Coupon redemption through Neko Proxy API.
- `/public/status` migration.
- Removal of the legacy bridge, `launcher_v2`, or Supabase code.
- Installer, updater, release-channel, or trust-profile changes.
- Any production enablement or publication.

The Proxy API repository now implements claim/heartbeat/release in slice 2A;
launch-permit, coupons, and `/public/status` remain slice 2B. Nothing is
deployed. The launcher client and Core path are implemented against the frozen
contract, but no live permit has been obtained and no staging E2E is claimed.

## 4. Frozen 5.1.6 behavior

`5.1.6` continues to use its existing password/recovery backend, Supabase
client, legacy permit Edge Function, installer, and update feed. The new flag
does not change the legacy build path, and the new path is rejected in frozen
builds. Do not re-point, rebuild, or publish `5.1.6` as part of this work.

## 5. Feature flags and gate

| Variable | Current behavior |
| --- | --- |
| `NEKO_PROXY_API_URL` | New-line switch. Unset = disabled. Must be an HTTPS origin with no path/query/fragment. Mutually exclusive with `NEKO_AUTH_BRIDGE_URL`. Rejected in frozen builds. |
| `NEKO_IDENTITY_BASE_URL` | Optional identity origin override; defaults to the existing identity origin. |
| `NEKO_AUTH_BRIDGE_URL` | Legacy bridge only. Still required for the old source/dev bridge path; cannot be combined with `NEKO_PROXY_API_URL`. |
| `NEKO_WEB_AUTH_ENABLED` | Legacy bridge enablement; the new path is enabled by `NEKO_PROXY_API_URL` itself. |
| `NEKO_WEB_AUTH_ONLY` | New path is always web-only; `0` is rejected with `NEKO_PROXY_API_URL`. |
| `NEKO_LAUNCHER_SCHEMA` | Legacy only; not used by the new path. |

Rollout gate:

- source/dev only;
- no frozen/release build;
- no production endpoint or account;
- no publication, tag, or installer/updater change;
- do not remove the bridge or `launcher_v2` until the `5.3.0` removal gate.

## 6. Current limitations and open questions

- Identity slice 1 code implements the refresh-token grant and rotation in its
  repo, but it is not deployed; staging still serves the old token. A real
  staging login waits for the identity deploy.
- Proxy API slice 2A implements claim/heartbeat/release in its repo; launch
  permit remains slice 2B. Nothing is deployed; live permit verification and
  E2E remain blocked.
- `/v1/me` is parsed for `identity_user_id`, `proxy_account_id`, `status`, and
  `display_name`. The license summary and ban/app-access fields are not yet
  consumed; claim supplies `license_valid_until`.
- The proxy status display still uses the existing Control Room endpoint; it is
  not yet migrated to Neko Proxy API `/public/status`.
- The installer-credential startup check stays enabled. Slice 2 now uses the
  installation key hash for claim, so the credential is required for the proxy
  path; removing or bypassing the check is not part of this slice.
- Refresh revocation/logout is local-only because contract v0 has no identity
  revocation endpoint.
- Refresh is fail-closed: any failed or ambiguous refresh clears the stored
  token and requires interactive login; there is no grace window.
- Error mapping, retry policy, and the removal map are defined in
  [proxy-api-launcher-contract.md](proxy-api-launcher-contract.md).
- The general P0 contract register remains at
  [docs/contracts/gap-and-conflict-register.md](../contracts/gap-and-conflict-register.md).
