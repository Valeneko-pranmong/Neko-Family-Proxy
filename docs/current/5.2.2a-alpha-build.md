## Installer fix — netfilter2 elevated command

The first revision-2 installer showed `FAIL: invalid pinned nfdriver.sha256`
when the netfilter2 step requested elevation. The elevated `cmd /c` command
appended one extra trailing quote, so PowerShell received the last pinned hash
(`ExpectedNfDriverSha256`) with a quote attached; the unelevated precheck was
unaffected. The command now closes with a single trailing quote, and
`tests/test_installer_separation_guard.py` guards the source line.

Command-level proof with the exact quoting:

| Form | Result |
| --- | --- |
| Old (extra `""`) | `FAIL: invalid pinned nfdriver.sha256`, exit 2 |
| Fixed (`"`) | `netfilter2 absent; registration required`, exit 10 |

The final silent install used `/SKIPDRIVER=1`, but the driver is now
installed and running on the release host from the operator/test run; see
below. Installation files and the rest of the installer were verified with
`/SKIPDRIVER=1`.

## Revision 5 code-review and hardening

- **Update-state evidence poisoning fixed.** Superseded, failed, and
  pre-commit-abort evidence entries are pruned at the next begin/commit/abort/
  rollback, and generation building accepts authenticated extra evidence
  instead of failing closed on stale entries. Without this, a third update
  after two successful commits could be rejected with `STATE_CORRUPT`.
- **Core-update memory and deadline fixes.** Pending-load, apply handoff, Core
  inventory, and generation hashing are streaming (no whole-file reads of the
  ~1 GiB Core artifact). The updater's APPLY deadline is 900 s and its
  release-wait grace period is 120 s instead of 5 s.
- **Installer execution hardened.** The elevated driver helper is no longer a
  user-writable `.cmd`: Inno passes a PowerShell wrapper that reads the script
  bytes once, verifies their SHA-256 against a build pin, and executes the same
  in-memory bytes via `ScriptBlock`. The wrapper runs 64-bit Sysnative
  PowerShell. The driver manifest is likewise read and hashed from one byte
  array, and the secure stage now lives under Program Files with reparse-point
  checks.
- **Installer cleanup fixed.** Install/uninstall now remove `update-pending`,
  `incoming`, `staging`, `NekoLauncher.exe.new`, and `NekoLauncher.exe.old`;
  a 1 GiB staged Core can no longer survive uninstall.
- **Core inventory tightened.** The post-install verifier rejects undeclared
  files, and the build gate rejects path traversal, duplicate paths, and
  undeclared CoreBundle files.
- **UI robustness.** File-repair completion is marshalled back to the Tk
  thread; background process/heartbeat polls no longer clear error toasts; a
  failed render/callback no longer stops the UI event pump; tray Exit re-arms
  after a declined close.
- **Frozen-build weight.** Supabase/pydantic are excluded from the frozen
  launcher (frozen builds are Proxy API + web-auth only); the updater no
  longer bundles Tcl/Tk and instead self-tests the candidate launcher's Tk
  runtime out-of-process. Launcher size fell 25,546,753 → 21,629,808 bytes
  (−15.3%); updater 14,326,535 → 11,281,237 (−21.3%); installer
  207,854,361 → 201,007,176 (−3.3%).
- **Alpha channel classification.** Preview-only guards now recognise
  `5.2.2a` / `5.2.2a0` (they previously classified the alpha as stable).

2026-10-27 main-integration hardening (repository tooling; not in the r6
installer): `release_controller.py` now fails closed when the trust profile is
missing or invalid, when the installer-embedded envelope/profile bytes are
missing or mismatched, or when no explicit ledger sequence allocation is
supplied. `clean-uninstall.ps1` now refuses elevated execution, requires the
Inno uninstaller to be a direct child of the app root with a canonical
`uninsNNN.exe` name, and supports a SHA-256 pin. `build_beta_installer.py` now
requires the input baseline envelope to be exactly canonical JSON; the r1–r6
envelopes carried a trailing newline that every earlier gate stripped before
checking, so the framing defect was baked into the installer unnoticed.
Remaining before publication: the r6 installer embeds the newline-terminated
envelope, so it must be rebuilt around the canonical 1,640-byte
`release-v2.json` (`71abac59…`) before the embedded/published hash equality in
`release_controller.py` and `publish_atomic_release.py` can hold; full
file-check hashing and some close/game-transition work still run on the Tk
thread (any such launcher change requires a rebuild); and the installer is not
Authenticode-signed.

## Publishing caveats

- The canonical `NekoProxyCore.zip` is confirmed on this host in the vault
    custody copy at `D:\Project manager\.vault\artifacts\core\`, size
    155,956,649 bytes and SHA-256 `5989064670…` — an exact match for the
    envelope's Core identity, and the installed `CoreBundle` verifies against
    manifest `c262432c…`.
- The r6 baseline envelope is 1,641 bytes with a trailing newline
    (`0a5f3fb3…`); the canonical form is 1,640 bytes (`71abac59…`). Clients
    download `release-v2.json` and parse the exact bytes without stripping, so
    the newline variant can never be published as the update asset, and the
    r6 installer embeds it. The canonical bytes are already signature-valid
    (the Ed25519 signature covers the decoded payload, not file framing) and
    equal what `release_controller.py` records for the ledger, so the fix is
    to re-stage the canonical envelope and rebuild the installer around it.
    This does not consume a new sequence.
- The installer is unsigned (no Authenticode certificate).
- Sequences 17–22 were consumed by the b17 test build and revisions 1–5;
  5.2.2a revision 6 uses sequence 23 so installed builds see a forward update.
- The installer is still unsigned. Authenticode signing is the highest-value
  remaining anti-tamper/anti-RE control; without it Windows cannot
  authenticate the publisher.
- Do not tag, publish, or deploy without owner sign-off.
