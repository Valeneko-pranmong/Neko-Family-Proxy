## Installer fix — netfilter2 elevated command

The first revision-2 installer showed `FAIL: invalid pinned nfdriver.sha256`
when the netfilter2 step requested elevation. The elevated `cmd /c` command
appended one extra trailing quote, so PowerShell received the last pinned hash
(`ExpectedNfDriverSha256`) with a quote attached; the unelevated precheck was
unaffected. The command now closes with a single trailing quote, and
`tests/test_installer_separation_guard.py` guards the source line.

Command-level proof with the exact quoting:

| Form | Result |
| --- | --- |
| Old (extra `""`) | `FAIL: invalid pinned nfdriver.sha256`, exit 2 |
| Fixed (`"`) | `netfilter2 absent; registration required`, exit 10 |

The final silent install used `/SKIPDRIVER=1`, but the driver is now
installed and running on the release host from the operator/test run; see
below. Installation files and the rest of the installer were verified with
`/SKIPDRIVER=1`.

## Revision 5 code-review and hardening

- **Update-state evidence poisoning fixed.** Superseded, failed, and
  pre-commit-abort evidence entries are pruned at the next begin/commit/abort/
  rollback, and generation building accepts authenticated extra evidence
  instead of failing closed on stale entries. Without this, a third update
  after two successful commits could be rejected with `STATE_CORRUPT`.
- **Core-update memory and deadline fixes.** Pending-load, apply handoff, Core
  inventory, and generation hashing are streaming (no whole-file reads of the
  ~1 GiB Core artifact). The updater's APPLY deadline is 900 s and its
  release-wait grace period is 120 s instead of 5 s.
- **Installer execution hardened.** The elevated driver helper is no longer a
  user-writable `.cmd`: Inno passes a PowerShell wrapper that reads the script
  bytes once, verifies their SHA-256 against a build pin, and executes the same
  in-memory bytes via `ScriptBlock`. The wrapper runs 64-bit Sysnative
  PowerShell. The driver manifest is likewise read and hashed from one byte
  array, and the secure stage now lives under Program Files with reparse-point
  checks.
- **Installer cleanup fixed.** Install/uninstall now remove `update-pending`,
  `incoming`, `staging`, `NekoLauncher.exe.new`, and `NekoLauncher.exe.old`;
  a 1 GiB staged Core can no longer survive uninstall.
- **Core inventory tightened.** The post-install verifier rejects undeclared
  files, and the build gate rejects path traversal, duplicate paths, and
  undeclared CoreBundle files.
- **UI robustness.** File-repair completion is marshalled back to the Tk
  thread; background process/heartbeat polls no longer clear error toasts; a
  failed render/callback no longer stops the UI event pump; tray Exit re-arms
  after a declined close.
- **Frozen-build weight.** Supabase/pydantic are excluded from the frozen
  launcher (frozen builds are Proxy API + web-auth only); the updater no
  longer bundles Tcl/Tk and instead self-tests the candidate launcher's Tk
  runtime out-of-process. Launcher size fell 25,546,753 → 21,629,808 bytes
  (−15.3%); updater 14,326,535 → 11,281,237 (−21.3%); installer
  207,854,361 → 201,007,176 (−3.3%).
- **Alpha channel classification.** Preview-only guards now recognise
  `5.2.2a` / `5.2.2a0` (they previously classified the alpha as stable).

2026-10-27 main-integration hardening (repository tooling; the builder gate is
in the revision 7 installer): `release_controller.py` now fails closed when the
trust profile is missing or invalid, when the installer-embedded
envelope/profile bytes are missing or mismatched, or when no explicit ledger
sequence allocation is supplied. `clean-uninstall.ps1` now refuses elevated
execution, requires the Inno uninstaller to be a direct child of the app root
with a canonical `uninsNNN.exe` name, and supports a SHA-256 pin.
`build_beta_installer.py` now requires the input baseline envelope to be
exactly canonical JSON; the r1–r6 envelopes carried a trailing newline that
every earlier gate stripped before checking, so the framing defect was baked
into the installer unnoticed. Revision 7 rebuilds the installer around the
canonical 1,640-byte `release-v2.json` (`71abac59…`) so the embedded and
published hashes agree; launcher, updater, Core, envelope payload, signature
and sequence 23 are unchanged, so no sequence was consumed.

## Revision 8 — Tk-thread freeze fixes

Revisions 1–7 accepted that "full file-check hashing and some
close/game-transition work still run on the Tk thread". Revision 8 removes
those stalls from the mainloop. Measured on the release host before the fix:
one `tasklist /FO CSV /NH` snapshot costs **315–360 ms**, and the 3-second game
poll took two of them — the coarse probe on a worker, then the exact-target
revalidation inline on the Tk thread.

- **Settings file check no longer hashes on the Tk thread.** `AppWindow`
  submits `check_installed_files` (Launcher + Updater + Core identity, plus
  `verify_installed_updater`) to `_update_executor` and marshals the report back
  through a `root.after` poll, the same pattern revision 7 already used for
  file repair. `SettingsWindow.set_file_check_busy()` disables the button and
  shows "กำลังตรวจสอบไฟล์ติดตั้ง…" while the worker runs;
  `finish_file_check()` renders the report or an honest failure notice, and a
  second click is ignored while a check is in flight. Warm-cache cost of the
  work that moved off the mainloop is ~21 ms on this host and seconds on a
  cold cache or a scanning host.
- **Game-process observation is fully off the Tk thread.** `_poll_game_process`
  now submits `_observe_game_process`, which resolves the coarse probe *and*
  the exact pso2.exe revalidation in one background step and hands
  `_on_game_detected` a finished answer (`revalidated=True`). The unconditional
  exact revalidation of every positive poll is preserved; only its thread
  changed. `_observe_runtime_health` queues `_revalidate_bound_game` instead of
  snapshotting inline, with a single-flight guard so repeated unhealthy
  telemetry renders cannot pile up probes.
- **Close no longer leaves a dead frame.** `_perform_close` withdraws the
  window and pumps idle tasks before the teardown that waits on child-process
  exits (`game_process_manager.stop(timeout=5.0)`) and the 0.75 s session-release
  join. That teardown itself stays synchronous and in order — pending-update
  release remains the last handoff action before `quit()`/`destroy()` — so the
  update handoff contract is unchanged.
- **Still on the Tk thread, deliberately:** the one-per-session
  `_startup_process_probe` in `_route_after_authentication`, and the close
  child-process/updater-handoff waits above. Both are bounded and were traded
  against handoff correctness.
- **Tests:** 2,821 → 2,826 passed (+5 regression tests: hashing off-thread with
  worker-thread proof, double-click suppression, busy-state delivery, poll
  observation off-thread, close withdraw ordering). The reconnect-suite
  harness gained `settle_game_observation()` to deliver the now-async probes;
  every original assertion about "only one queued reconnect" and
  "unconditional exact revalidation" still holds.

preview-0024 was required because `build_beta_installer.py` fails closed when
the baseline envelope's launcher installed identity does not match the staged
`NekoLauncher.exe`, so a changed binary forces a new envelope and a new
sequence. The envelope was canonicalized, signed, and cryptographically
verified by `build_software_release_v2.py` using the release key copy at

Remaining before publication: the installer is not Authenticode-signed (no

## Publishing caveats

- The canonical `NekoProxyCore.zip` is confirmed on this host in the vault
  custody copy at `D:\Project manager\.vault\artifacts\core\`, size
  155,956,649 bytes and SHA-256 `5989064670…` — an exact match for the
  envelope's Core identity, and the installed `CoreBundle` verifies against
  manifest `c262432c…`.
- Resolved in revision 7: the revision 1–6 envelopes are 1,641 bytes with a
  trailing newline (`0a5f3fb3…`) while the canonical form is 1,640 bytes
  (`71abac59…`). Clients download `release-v2.json` and parse the exact bytes
  without stripping, so the newline variant can never be published as the
  update asset, and `release_controller.py` and `publish_atomic_release.py`
  require it to hash-match the copy embedded in the installer. The canonical
  bytes were already signature-valid — the Ed25519 signature covers the
  decoded payload, not file framing — so revision 7 re-stages and re-embeds
  them without re-signing or consuming a sequence.
- The installer is unsigned. Authenticode signing is the highest-value
  remaining anti-tamper/anti-RE control; without it Windows cannot
  authenticate the publisher.
- Sequences 17–22 were consumed by the b17 test build and revisions 1–5;
  5.2.2a revisions 6 and 7 use sequence 23, and revision 8 uses sequence 24 so
  installed builds see a forward update. Revision 8's envelope was signed on
  this host from the release-key copy at
  `D:\Project manager\pem-archive\build-custody\neko-update-prod-3.pem`
  (passed through `NEKO_RELEASE_KEY_REF`, so no second key copy was created)
  and **no `authority/production_sequence_ledger.jsonl` record was written —
  that ledger is on the custody host. The owner must allocate/confirm sequence
  24 there before any publication.**
- Signing used `build_software_release_v2.py`; `sign_software_release.py` cannot
  sign a release-v2 payload because it parses through the legacy
  `parse_release_set`, which accepts only schema_version 1 with
  `channel = "beta"`.
- Do not tag, publish, or deploy without owner sign-off.
